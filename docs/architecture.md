# Architecture

Meshery Server installs the Meshery Operator into a cluster on connection and
thereafter manages its health and configuration. The operator owns two custom
resources and reconciles each into concrete workloads.

```
Meshery Server ──(installs & manages via pkg/client typed clientset)──▶ Meshery Operator (manager Deployment)
                                                                          │
                        ┌─────────────────────────────────────────────────┴───────────────┐
                        ▼                                                                   ▼
                 Broker controller                                                  MeshSync controller
                 reconciles Broker CR                                               reconciles MeshSync CR
                        │                                                                   │
            ┌───────────┼───────────────┐                                                   ▼
            ▼           ▼               ▼                                              Deployment
       StatefulSet   Service        2x ConfigMap                                       meshery/meshsync
        (NATS)       (client)       (nats.conf, accounts)                              BROKER_URL env
                        │
                        └──▶ endpoint derivation ──▶ Broker.Status.Endpoint.{Internal,External}
                                                              │
                                                              └──▶ injected as the MeshSync broker URL
```

## Custom resources (`api/v1alpha1`, `api/v1alpha2`)

- **`Broker`** (`brokers.meshery.io`) - a NATS message broker. Spec carries
  `Size`, `Version` (the NATS image tag), and a `Service` block for network
  exposure; `Status` carries `Endpoint{Internal,External}` and typed
  `Conditions`.
- **`MeshSync`** (`meshsyncs.meshery.io`) - the cluster-state synchronizer. Spec
  carries `Size`, `Version`, a `Broker` reference (native or custom URL), and a
  `WatchList`. `Status` carries `PublishingTo` and `Conditions`.

Both are namespaced, `apiextensions.k8s.io/v1`, group `meshery.io`, generated by
`controller-gen`. The CRD bases live in `config/crd/bases/`.

### Versioning and conversion

`v1alpha2` is the **conversion hub** (the storage version; `Hub()` in
`api/v1alpha2/conversion.go`). `v1alpha1` is a **spoke** that round-trips to it
via JSON (`api/v1alpha1/conversion.go`) - the two schemas are currently
field-identical, so this is a lossless copy; when they diverge, replace the
round-trip with explicit field mapping. `cmd/main.go` registers the conversion
webhook for both `Broker` and `MeshSync`; the CRDs declare `strategy: Webhook`,
so the webhook must be running for either version to be served.

## Controllers (`controllers/`)

Both reconcilers follow the same shape (`Reconcile` → finalizer → main reconcile
→ health check → status patch) and implement:

- **Finalizers** - owned objects are cleaned up on delete before the finalizer
  clears.
- **Typed status `Conditions`** via `meta.SetStatusCondition`.
- **An "update existing owned object" path** - on reconcile, existing owned
  objects are synced toward the desired spec.

Each `Reconcile` uses one `defer` with **named return values** to record
`pkg/metrics` (count/duration/errors) on every exit path - see
[metrics.md](metrics.md) for why named returns are required.

`main.go`/`cmd/main.go` wires both reconcilers into a single controller-runtime
manager with leader election (stable lease `meshery-operator-leader.meshery.io`),
`healthz`/`readyz`, and a metrics server.

### Known structural debt (tracked in the modernization plan)

- The reconcile sync overwrites `existing.Spec = desired.Spec` and gates on
  `Semantic.DeepEqual`, which fights server-defaulted fields and can hot-loop.
  Server-Side Apply replaces this in WS-3 (#785).
- Only the primary workload is `Owns()`'d; the broker `Service`/`ConfigMap`s are
  not watched, so endpoint changes are not re-triggered (WS-3).
- Endpoint derivation performs blocking TCP dials in the reconcile path; it
  becomes a pure, non-blocking function over the `Service` in WS-3/WS-4.

## Resource builders (`pkg/broker`, `pkg/meshsync`)

Workload manifests are produced two different ways, one per CRD:

- `pkg/broker/` - the NATS `StatefulSet`, client `Service`, and `nats.conf`/accounts
  `ConfigMap`s are **not** hand-authored. They are rendered from the official
  `nats/nats` Helm chart into `pkg/broker/manifests/nats.gen.yaml` at build time
  (`make nats-manifests`), embedded via `go:embed` (`pkg/broker/embed.go`), then
  decoded once and Server-Side-Applied by the controller (details below).
- `pkg/meshsync/resources.go` - the MeshSync `Deployment` is a hand-authored Go
  struct (no Helm, no embedded YAML).

`pkg/broker/broker.go` derives the broker endpoint and checks health via
`ReadyReplicas`. `pkg/meshsync/meshsync.go` injects the broker URL and checks
health. MeshSync's container probes are version-gated (`applyProbes`): pods
running MeshSync ≥ v1.0.1 - the first release that serves `/healthz` (liveness)
and `/readyz` (readiness, 503 until the broker connects) on the client port -
get httpGet probes, while older images, moving channel tags a user pins
explicitly, and unparseable versions keep an exec liveness probe as the
version-skew-safe fallback (an httpGet probe against an image without the
endpoints would connection-refuse and crashloop it).

### Broker upgrade cleanup

Earlier broker builders named their StatefulSet and LoadBalancer Service after
the Broker CR. The chart-based builder uses `meshery-nats` instead. Normal
reconciliation now prunes the verified legacy StatefulSet and Service after
publishing the replacement endpoint. This is separate from Broker finalization.

A candidate must be in the Broker namespace, named after that Broker, carry
`app=meshery,component=broker`, and have a controlling `meshery.io` Broker owner
reference matching the CR's name and UID. Both served owner-reference versions
are accepted. Current desired identities are explicitly protected, including
when the Broker itself is named `meshery-nats`. ConfigMaps, Secrets, PVCs and
other names are outside this migration's deletion scope.

Cleanup waits for the replacement StatefulSet's observed generation, updated
replicas, ready replicas and revisions to show a completed rollout. It also
waits for every MeshSync referencing that native Broker, including references
from other namespaces, to have a completed Deployment rollout with the new
`BROKER_URL` and auth Secret reference. The Broker endpoint is published **before**
this check, so consumers can migrate. Cleanup retries after one minute when the
migration gate is closed and no child is deleting. Issued or pending deletions
use a five-second retry; already deleting children do not need to pass that gate
again. Children not yet deleting still require the migration gate to open before
a delete can be requested. Owned resource events can trigger an earlier
reconciliation. This cleanup-specific retry policy applies after normal Broker
reconciliation and health checks succeed; errors still use controller-runtime
backoff. Neither cleanup retry blocks publication of the endpoint.

Environment matching requires the expected literal `BROKER_URL` and the token
Secret's name and key. An omitted Secret `optional` flag and explicit `false`
are equivalent. Optional token Secrets, different sources, literal tokens and
wrong endpoints or Secret references still block cleanup. Broker variables must
have unique names, and `NATS_TOKEN` must precede a `BROKER_URL` that expands it;
otherwise the stored configuration cannot establish the expected authentication.

These checks establish Kubernetes rollout state, not the absence of arbitrary
clients on the old NATS server. Older MeshSync images have weaker readiness
signals. Custom brokers and external clients are not discoverable through native
Broker references; users must plan their endpoint migration as part of the upgrade.

Deletes use UID and resourceVersion preconditions. A stale candidate is
re-evaluated after a conflict; NotFound is harmless. Other API failures surface
as a structured error and a false Broker `Cleanup` condition, which clears after
cleanup succeeds. Each accepted delete request emits an
`ObsoleteBrokerResourceCleanup` Kubernetes Event. The event reports a request,
not completion of Pod termination or cloud LoadBalancer deprovisioning.

The migration does not depend on the MeshSync deployment-strategy fix in #941.
Until a referenced MeshSync rollout can finish, legacy resources are retained.

### Managed-component images

Every managed-component image resolves through one path, `resolveVersion` for
MeshSync and `overlayBrokerSpec` for the broker, and both share
`pkg/utils/image.go`:

- **The default is a pinned release, never a channel tag.** An unset
  `spec.version` resolves to `defaultMeshSyncVersion` (MeshSync) or whatever the
  vendored chart rendered (NATS). A moving default re-points under running
  clusters, so an install that worked yesterday pulls a different image
  tomorrow; see [docs/release-process.md § Pinned images](release-process.md#pinned-images)
  for the failure this closes and the automation that keeps each pin fresh.
- **`spec.version` is honoured**, and a leading `v` is normalised off an
  otherwise-semver tag: these registries publish bare-semver image tags while
  their releases are v-prefixed, so `v1.0.3` copied from a release name would
  otherwise 404.
- **The pull policy follows the tag's mutability** (`utils.PullPolicyFor`):
  `Always` for a moving tag a user pinned deliberately, `IfNotPresent` for an
  immutable one, so side-loaded (kind) and air-gapped clusters work. kubelet's
  own default cannot do this - it infers `Always` from the literal `:latest`
  alone and would leave `stable-latest` on `IfNotPresent`.
- Because the resolved version feeds probe selection too, the pinned default is
  provably ≥ v1.0.1 and gets the httpGet probes rather than the fallback.

### MeshSync identity and RBAC (`MESHSYNC_SERVICE_ACCOUNT`)

MeshSync pods run under their **own ServiceAccount**, not the operator's. The
operator is least-privilege (#782): it may write only what it manages and read
almost nothing else. MeshSync needs the opposite: cluster-wide read and no write.
Sharing one identity forces one of them to be wrong, and since the operator went
least-privilege it was MeshSync: every watch failed with `forbidden`.

- **Selection.** The operator reads `MESHSYNC_SERVICE_ACCOUNT` once at startup
  (`pkg/meshsync.ResolveServiceAccountName`) and applies it to every MeshSync
  Deployment (`WithServiceAccountName`). Unset, it keeps the legacy default, the
  operator's own `meshery-operator` ServiceAccount, so charts that do not create
  the dedicated ServiceAccount keep scheduling MeshSync pods. An invalid name stops
  the operator at startup with `ErrInvalidServiceAccountName` rather than applying a
  Deployment the API server rejects on every reconcile.
- **Namespace.** A pod can only use a ServiceAccount in its own namespace, so the
  ServiceAccount must exist in each MeshSync CR's namespace. The shipped
  configuration (and the chart) put the operator, the CRs and the ServiceAccount in
  `meshery`. The legacy default had the same constraint.
- **What ships.** `config/manager/meshsync_service_account.yaml`
  (`meshery-meshsync`), `config/rbac/meshsync_workload_role.yaml`
  (`meshery-meshsync-role`) and `config/rbac/meshsync_workload_role_binding.yaml`
  (`meshery-meshsync-rolebinding`), with the env var set in
  `config/manager/manager.yaml`. The ServiceAccount sits beside the operator's in
  `config/manager`, unprefixed: placed in `config/rbac`, that directory's
  `namePrefix` plus kustomize's name-reference resolution rendered the binding
  subject as `meshsync`, binding nothing.
  `TestRenderedInstallManifestWiresMeshSyncServiceAccount` checks the rendered
  `config/manifests/default.yaml` end to end.
- **Why wildcard read.** The role grants `get`/`list`/`watch` on `*`/`*` and
  nothing else. MeshSync's watch set is open-ended: its default pipeline spans
  dozens of kinds across many API groups, including cluster-scoped ones (nodes,
  persistentvolumes, storageclasses, clusterroles, apiservices); the MeshSync CR's
  watch-list is user-editable; and MeshSync watches CustomResourceDefinitions and
  starts an informer for every CRD it finds at runtime. CRD groups cannot be
  enumerated at install time, so an explicit list reproduces the `forbidden`
  failure for every kind left off it. MeshSync performs no writes, so the verbs
  are the boundary. It is strictly narrower than the `*`/`*`/all-verbs role
  MeshSync had before 1.0. Trivy reports it as KSV-0046 ("manage all
  resources", a check that ignores verbs); `.trivyignore.yaml` excludes that
  check for this role's files only, so a wildcard anywhere else still surfaces.
- **What wildcard read includes.** Every Secret in the cluster (Secrets are in
  MeshSync's default watch list anyway), and `get` on subresources: `pods/log`
  (which log streaming uses) and the proxy subresources (`nodes/proxy`,
  `services/proxy`, `pods/proxy`). Clusters that narrow MeshSync's watch-list can
  swap in an enumerated role.
- **Interactive exec is not granted.** MeshSync's exec sessions need `create` on
  `pods/exec`, a write-class permission. Bind an additional role to
  `meshery-meshsync` to opt in.
- **Cross-repo contract.** The three names and the env var value are shared with
  the meshery-operator Helm chart in meshery/meshery, which creates the same
  objects and sets `MESHSYNC_SERVICE_ACCOUNT=meshery-meshsync`. See
  [release-process.md § Invariants](release-process.md#invariants) for release
  ordering.

### Vendored NATS chart (`pkg/broker/chart/`, `pkg/broker/manifests/nats.gen.yaml`)

The vendored NATS topology is rendered at build time from the pinned official
`nats/nats` Helm chart (`NATS_CHART_VERSION` in the Makefile) plus
`pkg/broker/chart/values.yaml`. Helm is a dev-time-only tool; the operator has
no Helm runtime dependency and applies the rendered manifest itself. Change the
NATS topology by editing `pkg/broker/chart/values.yaml` (or bumping the chart
version), then run `make nats-manifests`. CI has a drift gate for the rendered
output.

## Typed client (`pkg/client/v1alpha1`)

A hand-rolled typed clientset (`Brokers(ns)`, `MeshSyncs(ns)` with
Create/Get/Update/Delete/List/Watch/Patch) exported for **Meshery Server**, which
is the operator's primary consumer. Any change to the `v1alpha1` contract must
preserve this surface; see the modernization plan's compatibility section.

## Packaging

- `config/` - Kustomize bases assembled by `config/default`.
- `bundle/` - the OLM bundle (ClusterServiceManifest + CRDs) for operator-catalog
  distribution, generated by `operator-sdk` from `config/manifests`.
